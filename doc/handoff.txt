## 4. Architecture in 60 seconds (details: `REFERENCE.md`)

- `core.user.js` (`@run-at document-start`, `@grant none`) exposes `window.Core`. It reads `addons.json`, fetches each addon's code, caches it in `localStorage` (`core:code:<id>`), and runs it with `Core` in scope (`new Function`, falling back to an inline script). Addons update in the background (checked at most every 10 min) and apply on the **next** page load.
- `Core.float.add({id,title,icon,order,width,render,onShow,onHide})` is the **only** way to get a floating button + panel. Core draws the button in a shared dock row, owns the modal, and calls `render(el)`. There is **no hub** (the user explicitly rejected one).
- Other API: `Core.net` (cached, de-duplicated fetches + invalidation after POSTs), `Core.pages.*`, `Core.ui` (toast/modal/menu/h/btn/css), `Core.store`, `Core.state`, `Core.on/emit`, `Core.dom.watch/when`, `Core.cookies.withMode`, `Core.player.id()`, `Core.module(...)`.
- The three presets addons keep their original storage keys so users' data carries over: `pcPresets_<pid>`, `gearPresets_<pid>`, `petPresets_<pid>`. **Never change those keys or the preset data shape in a breaking way.**
- Globals/CSS/storage are prefixed `Core` / `core-` / `core:`. (Originally "DS"; the user hated that name. `ds:` keys are obsolete leftovers.)

## 5. The two update paths (the #1 source of confusion — read twice)

| Code lives in | Reaches users how |
|---|---|
| `addons/*.js` on GitHub | automatically (≤10 min check, GitHub raw CDN can lag ~5 min), then "reload to apply" |
| **`core.user.js`** (the copy inside Tampermonkey) | **not** from the addon files. Needs a **`@version` bump** + push to GitHub (header has `@updateURL`/`@downloadURL` to the raw URL, so Tampermonkey updates ~daily) or the user reinstalls from the raw link / pastes it in |

Core owns: floating buttons, modal shell/scroller/close button, toasts, menus, the ⚙️ manager, the loader. **Every time you change `core.user.js`: bump `@version` and `version:`** (and the `jsdom_smoke` regex accepts any semver). Tell the user to update the Tampermonkey copy and how to verify: ⚙️ top line shows `Core v…`, or `Core.version` in the console. Whenever you change an addon, bump its `version` in `addons.json`.

Previously the user reloaded "many times" with no change because only addon files had been pushed while the fix was in `core.user.js`. Don't assume a code change is live; say which file it lives in.

## 6. Deployment facts

- Repo: `https://github.com/WerewuIf/UI-Core`, **public**, branch `main`, files at repo root.
- Manifest default in `core.user.js`: `https://raw.githubusercontent.com/WerewuIf/UI-Core/main/addons.json`. Addon URLs in `addons.json` are relative to it. Install link for users: `https://raw.githubusercontent.com/WerewuIf/UI-Core/main/core.user.js`.
- **CORS trap:** `github.com/<u>/<r>/raw/...` (GitHub's "Copy raw file") is a redirect the browser blocks from the game's site ("Access-Control-Allow-Origin … invalid value ''"). Core now rewrites `github.com/.../raw|blob/...` to `raw.githubusercontent.com/...` automatically (`normalizeUrl`), and falls back to a saved copy of an addon if the network fails or the URL changed. Keep both behaviours.
- Users must turn off the old standalone scripts or everything runs twice.
- Optional hardening in the manifest: `sha256` per addon (refuses to run on mismatch). Security note: whoever can push to the repo runs code inside players' logged-in sessions, so recommend 2FA.

## 8. Things that were learned the hard way

1. **Player id.** Pages differ: most have `.side-drawer a[href*="player.php?pid="]`, but the event map has no sidebar. `Core.player.id()` tries sidebar → `window.expPotionSettings.userId` → `#ecConfig` JSON `userId` → last seen id (`core:lastPid`) → `'default'`. All addons must use it; a hand-rolled lookup made presets look empty (and saved to `_default`).
2. **Dock placement.** The dock sits level with the site's own buttons (`bottom:17px`), slides left in 4 px steps to clear fixed elements, and **stacks above** them on narrow screens (a 4-button row can't fit between ☰ and the site's ⚔️ at ~390 px). It treats small fixed *groups* (e.g. a column of zoom buttons) by inspecting their child buttons, and ignores overlays/drawers (≥60% of the viewport). Must never run off-screen.
3. **Cache check.** An old bug required cached code's URL to equal the current URL, so a manifest URL change discarded working code. Fixed (`readAnyCode` fallback).
4. **`ui.css` before `<head>` exists** now defers until DOM is available.
5. **Scroll.** Top-level panel node must not set `overflow`/`max-height`. Nested bounded lists inside dialogs (picker grids, crystal editor grid) are fine but their scrollbars are hidden too.
6. **Harness replaced placeholder bug:** tests swap `CONFIG.manifest` by regex (`core_text()`), so changing the default URL never breaks them.

## 10. How the pets sigil/orb logic works (so you can extend it)

In `pet-presets.js`: `SIGIL_SLOTS = ['attack','defense','elemental']`, `SIGIL_LABELS`, `SIGIL_EMPTY_ICON`, `SIGIL_NONE()`, `sigilSlotOf(el)`. A preset stores `sigils: { <petInvId>: {attack, defense, elemental} }` (item ids) and `meta.sigils[itemId]` (name/image). **A missing slot key means "don't touch"** (that is how old presets stay safe). Capture (`captureCurrentToPreset`) loops `SIGIL_SLOTS` calling `fetchSigilInfo`. Restore (`restorePresetToTeam`) runs `sigilRemovalPass` (take off what shouldn't be there) then `sigilEquipPass`, using `findSigilHolder` / `findAllSigilHolders` for items worn by pets outside the preset (forced take-over, `CFG.FORCE_SIGILS`, default true; `CFG.TAKE_FROM_OTHER_TEAMS` for pets). DOM scanners (`scanSigilWearers`, `readCardSigilNames`, `collectSigilWearers`, `presetSigilsMatch`) classify slots by CSS class via `sigilSlotOf`; `installSigilOverride` hooks the page's own sigil modal. Editor chips: `buildSigilLayer` makes `.pp-sigil-layer` with two rows (`.pp-sigil-row`): row 1 = C, row 2 = A B; `pickerSigilChip` + `.pp-picker-sigil-line` mirror this in the link picker; `openSigilChooser` is the chooser dialog. To add another slot type: add it to the constants, give it a chip class/icon, and add a fake in `dev/lib/petsmock.py` + a case in `pets_orb_test.py`.

## 11. How to work on a change (the workflow that has worked)

1. Read the relevant code (grep first; the addons are huge). Prefer **exact-match patches** (`str.replace` with an `assert old in s`) over rewrites. Never touch logic you were not asked to touch.
2. `node --check` every changed JS file.
3. Reproduce the user's problem or write the new behaviour as a test in `dev/tests/` **first when practical**, and confirm a test fails on the old code (copy the repo to `/tmp`, swap the old file, set `CORE_DIR=/tmp/copy/`). The user values proof that the test can catch the bug.
4. Run `bash dev/run_all.sh`. Look at screenshots (`dev/shots/`) for anything visual.
5. Bump versions (`core.user.js` if Core changed; `addons.json` for addons). Update `README.md` (basic!) / `REFERENCE.md` if behaviour or API changed.
6. Rebuild the zip with the top folder `core/` (exclude `dev/shots/` and `node_modules`), copy to `/mnt/user-data/outputs/`, and `present_files`.
7. Final message: what changed; what was verified and how; which file(s) the user must update where (Tampermonkey copy vs GitHub); what is **not** verified.

Environment notes for a Linux sandbox: Playwright + Chromium are usually available (`/opt/pw-browsers`); `pip install` needs `--break-system-packages`; `jsdom` via `npm i` in `dev/`. If the sandbox has no network, the tests still run (they mock everything).
